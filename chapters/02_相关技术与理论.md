# 第2章 相关技术与理论

本章介绍系统使用的主要技术,重点说明 RAG、向量检索、混合检索以及前后端框架,不展开与系统无直接关系的理论内容。

## 2.1 检索增强生成(RAG)技术

检索增强生成（Retrieval-Augmented Generation，RAG）是先从外部知识库检索资料,再由大语言模型根据资料生成回答的方法[7][9]。它把知识放在可以更新的文档和索引中,不需要重新训练模型,并可以把检索到的原文作为回答依据。因此,对于内容经常更新且需要核对出处的校园制度和办事指南,RAG 比只依赖模型内部知识更合适。

本系统的问答过程分为检索、增强和生成三步。系统先将问题转为查询向量,同时进行向量检索和关键词检索;然后把命中的切片按来源编号组织成上下文;最后交给模型生成回答。没有检索到足够证据时,系统直接返回拒答信息,不调用生成模型。

## 2.2 向量数据库与嵌入模型

嵌入模型（Embedding Model）把文本转换为稠密向量,语义相近的文本在向量空间中的距离更近,检索因此可以转化为近邻搜索。余弦相似度常用于比较两个向量的方向,本系统依据该相似度对候选切片排序,不再展开公式推导。

本系统使用 bge-m3 生成 1024 维向量,Qdrant 保存向量点并使用 COSINE 度量。PostgreSQL 保存文档、切片和元数据,切片主键同时作为 Qdrant 点标识。入库增强产生的关键词和候选问题只用于向量化,原始正文保持不变,便于引用时展示原文。

## 2.3 混合检索与重排技术

向量检索适合处理同义表达,关键词检索对编号、日期和专有名词等精确内容更稳定。图书馆问答等应用也表明,实际知识服务需要同时考虑语义检索和资料溯源[7]。本系统将两路结果结合:向量路在 Qdrant 中召回候选,关键词路使用 jieba 分词和二元切分后在数据库中匹配正文,两路结果再按权重融合。融合后统一进行阈值过滤,避免关键词独有的有效命中被提前丢弃。

在需要时,系统对过滤后的少量候选进行重排;重排失败时回退到融合结果。最终候选还会补充同一文档的相邻切片,以减少切块造成的语义断裂。上述过程分别承担召回、排序、去噪和上下文补充作用。

## 2.4 后端开发技术

后端使用 FastAPI 提供异步接口,使用 Pydantic v2 校验请求参数。代码按“路由—服务—RAG 管线”分层:路由负责请求和鉴权,服务层负责知识库、文档和会话等业务操作,RAG 管线负责解析、检索和生成。模型配置集中保存在配置文件中,切换配置后可以替换运行中的模型服务。

数据持久层使用异步 SQLAlchemy 和 PostgreSQL,保存知识库、文档、切片、会话及问答记录。文档由后台任务轮询领取,按解析、切块、增强和向量化等阶段更新进度。管理端使用 JWT,聊天端使用 X-Client-ID 匿名标识,两类接口按路径区分。

## 2.5 前端开发技术

前端采用 Vue 3 组合式 API 构建单页应用,配合 TypeScript 为组件属性、接口返回与状态数据提供静态类型检查,把接口字段拼写错误一类问题在编译阶段暴露出来;构建工具 Vite 提供快速启动与热模块更新,开发期通过代理把接口请求转发到后端,使前后端可以独立运行与部署。

回答内容使用 markdown-it 渲染,引用标记可以点击打开原始文件预览。问答接口使用服务器推送事件（Server-Sent Events，SSE）返回开始、增量文本、来源、完成和错误等事件,前端收到文本后即时追加到当前消息中。

## 2.6 本章小结

本章介绍了系统的主要技术。RAG 负责先检索再生成,向量数据库负责保存和召回语义向量,混合检索兼顾语义匹配与精确匹配,重排和邻块扩展用于改善候选证据。FastAPI、PostgreSQL、Vue 3 和 SSE 共同支撑系统的接口、数据和交互,具体设计见第4章。
